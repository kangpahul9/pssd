Problem: DerivativeSequence

First Idea:
Repeatedly compute the "derivative" of the sequence.
Replace each element with the difference between the next and the current.
After one pass, the sequence becomes one element shorter.
Do this n times.

Why it might work:
The problem definition says each "derivative" reduces the sequence by 1, and each element is just the difference of two consecutive elements. Repeating n times should directly give the answer.

Try #1 (Nested Loops):
for (int i = 0; i < n; i++) {
    for (int j = 0; j < a.size()-1; j++) {
        a[j] = a[j + 1] - a[j];
    }
    a.pop_back();
}

Reflection:
Bug: for (int j = 0; j < a.size(); j++). It accesses a[j+1] when j == a.size()-1, which is out-of-bounds. So run till j < a.size()-1.
After each full pass, call a.pop_back() to shrink array by one.
Tested on sample: worked fine after fixing bounds.



Problem: SimpleDuplicateRemover

First Idea:
We need to remove duplicates from a sequence of integers, but keep only the rightmost occurrence of each element.
Store the last index where each number occurs.
Then build the result by including only those elements at their last position.

Why it might work:
If we know the last occurrence of every element, then while scanning again, we only keep it if it’s the last time it appears. This way duplicates earlier in the sequence get skipped automatically.

Problem: TimeTravellingCellar

First Idea:
profit[i] = profit if cellar i is advanced in time.
decay[j] = loss if cellar j is turned back in time.

Why it might work:
Brute force is straightforward: just try all (i, j) pairs with i != j.

Try #1 (Double Loop):
for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        if (i == j) continue;
        maxProfit = max(maxProfit, profit[i] - decay[j]);
    }
}

Reflection:
Added if (i == j) continue; to avoid using the same cellar for both profit and decay.


Problem: PaternityTest

First Idea:
We need to determine which men could possibly be the father of a given child, given the mother's DNA string.

Why it might work:
Tracking isFather for impossible cases + counting matches (fatherMatches) directly encodes both rules.

Try #1:
for (int i = 0; i < men.size(); i++) {
    int fatherMatches = 0;
    bool isFather = true;

    for (int j = 0; j < n; j++) {
        if (child[j] == mother[j]) {
            if (child[j] == men[i][j]) fatherMatches++;
        } else {
            if (child[j] == men[i][j]) fatherMatches++;
            else { isFather = false; break; }
        }
    }
    if (isFather && fatherMatches >= n / 2) indices.push_back(i);
}

Reflection:
Counts matches even when both mother and father share the gene.
Correctly handles mandatory contributions when child[j] ≠ mother[j].

First Idea:
Use recursion + memoization or DP to count the number of sequences of length N.

Why it might work:
At each step, the number of ways to reach digit d of length len depends only on the counts from its neighbors at length len-1.

Try #2 (Bottom-up DP):
Build a DP table where dp[len][d] = number of ways to form a sequence of length len ending at digit d.
Initialize dp[1][d] = 1 for all digits (base case).
for (int len=2; len<=N; len++)
    for (int d=0; d<=9; d++)
        for (int nb : neighbors[d])
            dp[len][d] += dp[len-1][nb];
Finally, sum all dp[N][d] to get the answer.

Reflection:
Recursive approach was less efficient, so switched to iterative DP.
Learned that bottom-up DP is often cleaner than recursion for sequence-counting problems.

Weekly Reflection

This week I worked across problems involving brute force, arrays, dynamic programming, and condition-heavy logic.

What I Learned:
Brute force is often safe when constraints are small (TimeTravellingCellar).
Index tracking is powerful for removing duplicates (SimpleDuplicateRemover).
String/array condition checking must be systematic (PaternityTest).
Dynamic programming is a strong tool for sequence counting problems (UnsealTheSafe).

What I Could Improve:
Always initialize counters or accumulators to avoid undefined results.
Watch out for division by zero or invalid accesses in loops.
Be extra careful with loop ranges (DerivativeSequence showed this).
Spend time clarifying the rules in condition-heavy problems before coding.
Recognize when a DP formulation is cleaner and more scalable than recursion (lesson from UnsealTheSafe).

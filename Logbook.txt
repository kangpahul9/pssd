Problem: Thimbles

First Idea:
We start with 3 thimbles labeled 1, 2, and 3.
A small ball begins under thimble 1.
We are given a list of swaps (e.g., "1-3" or "2-3") that describe which two thimbles are swapped each time.
Our task is to determine which thimble the ball ends up under after all swaps are performed.

Initial Thought:
The simplest way is to simulate the process directly:
Start with ball = 1.
For each swap "a-b", if the ball is under a, move it to b;
if it’s under b, move it to a;
otherwise do nothing.

Why it might work:
Each swap only affects the ball’s position if it is currently under one of the swapped thimbles.
The ball’s position changes deterministically and there are only three possible thimbles, so direct simulation in a single pass is enough.
No advanced data structure or algorithm is needed — just careful parsing of the swap strings.

Try #1 (Simple Simulation):
int thimbleWithBall(vector<string> swaps) {
    int ball = 1;  // starts under thimble 1
    for (string s : swaps) {
        int a = s[0] - '0';
        int b = s[2] - '0';
        if (ball == a)
            ball = b;
        else if (ball == b)
            ball = a;
    }
    return ball;
}

Reflection:
This direct simulation approach is both the simplest and most efficient possible — it runs in O(n) for n swaps, and only uses a few integers.
No need for arrays or extra storage.



Problem: MatchNumbersEasy

First Idea:
We are given how many matchsticks are needed to make each digit (0–9).
With n matchsticks available, we must build the largest possible number (as a string) using any combination of digits.

Initial thought: 
Try every combination of digits using loops, compute how many matches they cost, and keep track of the largest numeric result.
We can start with a high-cost digit, subtract its cost, and keep adding cheaper digits as long as matches remain.

Why it might work:
Each digit consumes a fixed number of matches, and we are free to use any digits in any order.
By trying digits from highest to lowest, we maximize the leftmost (most significant) digit first.
Whenever we can still afford a digit’s cost, we append it to the current number.
We record the largest numeric value found.


Try #1 (Nested Loops + While Construction):
for (int i = matches.size() - 1; i >= 0; i--) {
    if (matches[i] > n) continue;
    left = n - matches[i];
    currMax = i;
    for (int j = matches.size() - 1; j >= 0; j--) {
        int tempLeft = left;
        long long tempNum = currMax;
        while (tempLeft >= matches[j]) {
            tempNum = tempNum * 10 + j;
            maxNumber = max(maxNumber, tempNum);
            tempLeft -= matches[j];
        }
    }
}

Reflection:
Originally, I used integer math (tempNum = tempNum * 10 + j), but that produced wrong results like "200" instead of "210".
The problem was that numeric concatenation (*10 + j) doesn’t preserve digit order context and breaks for large or variable-length numbers.
The DP-based approach is both optimal and elegant.
It transforms the problem into incremental string-building and comparison, which matches exactly how we think of forming the “largest” number.


Problem: CorporationSalary

First Idea:
Each employee’s salary is the sum of the salaries of their direct subordinates, and any employee with no subordinates has a salary of 1.
This problem is naturally represented as a directed acyclic graph (DAG), where edges go from a manager to their subordinates.

Why it might work:
Each person’s salary depends only on the salaries of their subordinates.
If we process subordinates first, then a manager’s salary is simply the sum of their children’s salaries.
This recursive dependency can be solved efficiently using Depth-First Search (DFS) with memoization.
Each employee’s salary is computed exactly once and stored for reuse.

Try #1 (DFS + Memoization):
long dfs(int i, vector<string>& rel, vector<long>& memo) {
        if (memo[i] != -1) return memo[i];

        long sum = 0;
        for (int j = 0; j < rel.size(); j++) {
            if (rel[i][j] == 'Y') {
                sum += dfs(j, rel, memo);
            }
        }

        if (sum == 0) sum = 1;  // no subordinates → salary = 1
        return memo[i] = sum;
    }

    long totalSalary(vector<string> relations) {
        int n = relations.size();
        vector<long> memo(n, -1);

        long total = 0;
        for (int i = 0; i < n; i++) {
            total += dfs(i, relations, memo);
        }

        return total;
    }

Reflection:
The recursive DFS approach is clean and effective.
Each node (employee) is visited only once thanks to memoization.



Problem: RockStar

First Idea:
This structure naturally represents transitions between “fast” and “slow” zones, similar to a two-state graph where songs are directed edges.

Why it might work:
We can’t reorder songs arbitrarily. Transitions follow strict start/end matching rules.
The album can therefore be built by chaining songs according to their end/start type, starting in the appropriate zone (fast if any fast-start songs exist, otherwise slow).

Try #1 (Case Analysis and Counting Logic):
 if (ff + fs == 0) {
            return ss + (sf > 0 ? 1 : 0);
        }

        if (fs == 0) {
            return ff;
        }

        int ans = ff;                
        ans += 1;                     
        ans += ss;                    
        ans += 2 * min(sf, fs - 1);  
        if (sf >= fs) ans += 1;      
        return ans;

Reflection:
The logic captures every way to transition between “fast” and “slow” segments.
Starting in the fast zone ensures all ff songs are used first.
Each fs/sf pair allows two extra songs — one in each direction — and leftover transitions are handled by the conditional at the end.
